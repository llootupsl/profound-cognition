# 对象路由器 — 八类对象分类路由规则

> **模块标识**: `knowledge/object-router`
> **作者**: 阿洋
> **依赖**: `tasks/T01_input_triage`
> **核心功能**: 为输入分流器（T01）提供对象类型分类的完整路由规则，确保 `object_type` 字段分类准确、边界清晰、冲突可解

---

## 1. 概述

对象路由器是 T01 输入分流器的核心分类引擎。它将用户输入的原始问题映射到八种预定义对象类型之一，为下游认知流水线提供精准的对象画像。

八种对象类型严格对齐 T01 的 `object_type` 枚举：

```
entity | event | concept | phenomenon | policy | technology | person | system
```

**分类原则**:
1. **唯一归属**: 每个输入问题必须且只能归入一种主类型
2. **语境优先**: 同一词汇在不同语境下可能归属不同类型，以问题实际指向为准
3. **层级可嵌**: 主类型确定后，`object_category` 字段可标注次级分类与跨类型关联
4. **歧义可解**: 边界冲突按优先矩阵裁决，不得输出模糊分类

---

## 2. 八类对象定义与路由规则

### 2.1 entity（实体）

**定义**: 具有独立身份标识的物理或概念性存在体。实体拥有可辨识的边界、持续存在的属性和可被指称的名称，是其他类型对象的承载者或作用对象。实体可以是具体的（组织、机构、地点、物品），也可以是概念性的（品牌、货币、法律主体）。

**判断标准**:
- 可被独立命名和指称
- 具有相对稳定的属性集合
- 可作为动作的发出者或承受者
- 在时间维度上具有持续性（非瞬时）

**关键词信号**（至少命中1个即触发候选分类）:
1. 公司 / 企业 / 集团 / 厂商
2. 组织 / 机构 / 团体 / 协会
3. 国家 / 地区 / 城市 / 地方
4. 品牌 / 商标 / 产品线
5. 银行 / 基金 / 交易所
6. 大学 / 医院 / 博物馆
7. 平台 / 生态 / 联盟
8. 资产 / 资源 / 设施 / 基础设施
9. 货币 / 证券 / 债券 / 期货
10. 宗教团体 / 教会 / 寺庙
11. 军队 / 部队 / 军事基地
12. 部门 / 委员会 / 局 / 厅
13. 社区 / 村落 / 部落
14. 数据库 / 知识库 / 档案馆
15. 航天器 / 舰船 / 载具
16. 矿产 / 能源 / 土地

**边界案例处理规则**:
- 当实体同时是技术载体时（如"华为"），以问题焦点判定：问组织运营→entity，问技术能力→technology
- 当实体是政策执行主体时（如"央行"），以问题焦点判定：问机构本身→entity，问其发布的政策→policy
- 虚拟实体（如"元宇宙"）若问题指向其作为空间/平台属性→entity，若指向其概念框架→concept

**跨类型映射规则**:
- entity ↔ person: 个人名义的企业家（如"马斯克"）在问个人经历时→person，在问其企业帝国时→entity
- entity ↔ system: 当实体的内部结构成为焦点时（如"欧盟的运作机制"），升级为system
- entity ↔ technology: 当实体作为技术实现载体被讨论时（如"特斯拉的自动驾驶"），跨映射至technology
- entity ↔ policy: 当实体是政策制定/执行主体时，`object_category` 标注政策关联

### 2.2 event（事件）

**定义**: 在特定时间范围内发生的、具有因果关联的客观事态变化。事件具有明确的时间锚点（发生时间）、空间定位和参与主体，是历史叙事和因果分析的基本单元。事件可以是瞬时的（爆炸、签约）或持续的（战争、运动）。

**判断标准**:
- 具有时间定位（何时发生/持续多久）
- 具有因果结构（起因→经过→结果）
- 涉及参与主体和受影响对象
- 具有可叙述的动态过程

**关键词信号**:
1. 事件 / 事故 / 案件 / 案件
2. 战争 / 冲突 / 对抗 / 交战
3. 选举 / 公投 / 就职 / 上台
4. 危机 / 灾难 / 灾害 / 事故
5. 会议 / 峰会 / 会谈 / 谈判
6. 罢工 / 游行 / 抗议 / 示威
7. 爆发 / 崩溃 / 垮塌 / 倒闭
8. 签约 / 并购 / 上市 / 退市
9. 发射 / 坠毁 / 碰撞 / 爆炸
10. 出台 / 发布 / 宣布 / 公布
11. 运动 / 革命 / 起义 / 政变
12. 诉讼 / 审判 / 裁决 / 判决
13. 恐袭 / 袭击 / 暗杀 / 绑架
14. 演讲 / 辩论 / 听证 / 质询
15. 开幕 / 闭幕 / 落成 / 揭幕
16. 暴跌 / 暴涨 / 熔断 / 崩盘

**边界案例处理规则**:
- 当事件与政策同时出现时（如"新法规颁布"），颁布行为本身→event，法规内容→policy
- 当事件成为现象的标志性案例时（如"硅谷银行倒闭"），问事件经过→event，问行业连锁反应→phenomenon
- 当事件涉及特定人物时（如"特朗普遇刺"），问事件本身→event，问人物影响→person

**跨类型映射规则**:
- event ↔ phenomenon: 单次发生→event，反复出现的模式→phenomenon
- event ↔ policy: 政策的颁布/签署是event，政策的内容/影响是policy
- event ↔ person: 事件中的人物是参与者，当问题焦点在事件过程→event，在人物角色→person
- event ↔ entity: 事件涉及的实体是承受者/发起者，焦点在事件→event，在实体→entity

### 2.3 concept（概念）

**定义**: 抽象的思想、理论或框架，用于理解、解释和组织现实世界。概念不具有物理实体，但具有逻辑结构和解释力，是学术论述和思想争鸣的核心对象。概念可以是哲学性的（自由、正义）、科学性的（熵、进化）、方法论的（范式、模型）。

**判断标准**:
- 具有抽象性，无法直接触摸或观测
- 具有定义性，可被精确定义或争议性定义
- 具有解释力，用于理解和组织经验
- 可跨领域迁移应用

**关键词信号**:
1. 理论 / 学说 / 主义 / 思想
2. 概念 / 范畴 / 范式 / 框架
3. 原理 / 原则 / 公理 / 定理
4. 哲学 / 认识论 / 本体论 / 伦理
5. 模型 / 假说 / 推论 / 推导
6. 价值 / 信仰 / 意识形态 / 世界观
7. 方法论 / 方法 / 逻辑 / 推理
8. 自由 / 民主 / 正义 / 平等
9. 熵 / 进化 / 相对论 / 量子
10. 结构主义 / 后现代 / 解构 / 建构
11. 博弈论 / 信息论 / 控制论 / 系统论
12. 唯物 / 唯心 / 辩证 / 实证
13. 人权 / 主权 / 法治 / 宪政
14. 资本主义 / 社会主义 / 共产主义 / 自由主义
15. 理性 / 感性 / 经验 / 先验
16. 本质 / 现象 / 存在 / 虚无

**边界案例处理规则**:
- 当概念已被技术实现时（如"人工智能"），问理论原理→concept，问工程实现→technology
- 当概念被政策采纳时（如"碳中和"），问概念内涵→concept，问政策执行→policy
- 当概念被用于解释现象时（如"通货膨胀"），问概念定义→concept，问实际表现→phenomenon

**跨类型映射规则**:
- concept ↔ technology: 概念是技术的理论基础，技术是概念的工程实现。问"是什么/为什么"→concept，问"怎么做/做了什么"→technology
- concept ↔ policy: 概念是政策的理念基础，政策是概念的制度化。问理论内涵→concept，问制度安排→policy
- concept ↔ phenomenon: 概念用于解释现象，现象是概念的经验证据。问定义和理论→concept，问观测和表现→phenomenon
- concept ↔ system: 概念是系统的设计理念，系统是概念的组织实现。问理论框架→concept，问运行机制→system

### 2.4 phenomenon（现象）

**定义**: 可被观察、测量和记录的规律性模式、趋势或异常状态。现象是经验层面的客观呈现，具有可重复性或可辨识的模式特征，是科学研究和趋势分析的核心对象。现象不同于事件——事件是单次发生，现象是模式化的重复呈现。

**判断标准**:
- 具有可观测性（可直接或间接观测）
- 具有模式性（非孤立事件，而是可辨识的模式）
- 具有趋势性或规律性
- 可被量化描述或统计刻画

**关键词信号**:
1. 趋势 / 走势 / 动向 / 演变
2. 现象 / 表现 / 征兆 / 特征
3. 增长 / 衰退 / 萎缩 / 扩张
4. 通胀 / 通缩 / 滞胀 / 泡沫
5. 老龄化 / 少子化 / 城镇化 / 贫困化
6. 全球化 / 逆全球化 / 区域化 / 本地化
7. 气候变化 / 变暖 / 变冷 / 极端天气
8. 流行 / 传播 / 扩散 / 蔓延
9. 不平等 / 分化 / 极化 / 分层
10. 周期 / 波动 / 震荡 / 循环
11. 迁移 / 流动 / 外流 / 回流
12. 内卷 / 躺平 / 消费穷尽重试替代 / 消费升级
13. 失业率 / 就业率 / 劳动参与率
14. 收敛 / 发散 / 突变 / 相变
15. 疫情 / 大流行 / 传染 / 感染潮
16. 产能过剩 / 供需失衡 / 结构性矛盾

**边界案例处理规则**:
- 当现象由特定事件触发时（如"金融危机"），问触发事件→event，问持续模式→phenomenon
- 当现象被政策干预时（如"房价上涨"），问市场表现→phenomenon，问调控措施→policy
- 当现象有技术驱动时（如"数字化转型"），问社会效应→phenomenon，问技术手段→technology

**跨类型映射规则**:
- phenomenon ↔ event: 单次→event，模式化重复→phenomenon。判断标准：是否具有可重复性/规律性
- phenomenon ↔ policy: 现象是政策的问题背景，政策是现象的干预手段。问"发生了什么"→phenomenon，问"如何应对"→policy
- phenomenon ↔ concept: 现象是经验层面的，概念是理论层面的。问"观察到了什么"→phenomenon，问"如何解释"→concept
- phenomenon ↔ technology: 技术可引发现象（如"信息茧房"），现象可催生技术需求。问社会表现→phenomenon，问技术方案→technology

### 2.5 policy（政策）

**定义**: 由权威主体制定并执行的规范性、制度性或治理性工具。政策具有明确的制定主体、适用范围、执行机制和法律/行政效力，是社会治理和制度变迁的核心手段。政策包括法律法规、行政规章、战略规划、国际条约等。

**判断标准**:
- 具有权威制定主体（政府、国际组织、监管机构）
- 具有规范性效力（约束、激励、禁止、许可）
- 具有适用范围和执行机制
- 具有政策目标与预期效果

**关键词信号**:
1. 政策 / 法规 / 法律 / 条例
2. 战略 / 规划 / 纲要 / 方案
3. 法案 / 修正案 / 决议 / 命令
4. 监管 / 管制 / 审批 / 备案
5. 补贴 / 减税 / 退税 / 豁免
6. 制裁 / 禁令 / 限制 / 封锁
7. 条约 / 协定 / 公约 / 协议
8. 改革 / 开放 / 试点 / 推广
9. 配额 / 关税 / 壁垒 / 准入
10. 标准 / 规范 / 准则 / 指南
11. 罚款 / 处罚 / 惩戒 / 追责
12. 刺激 / 紧缩 / 扩张 / 收缩
13. 产业政策 / 财政政策 / 货币政策 / 外交政策
14. 立法 / 执法 / 司法 / 修法
15. 特区 / 自贸区 / 开发区 / 保护区
16. 白皮书 / 蓝皮书 / 绿皮书 / 红头文件

**边界案例处理规则**:
- 当政策与事件交织时（如"巴黎协定签署"），签署行为→event，协定内容→policy
- 当政策引发现象时（如"双减政策后的教培行业"），问政策内容→policy，问行业变化→phenomenon
- 当政策涉及特定实体时（如"对华为的芯片禁令"），问政策本身→policy，问实体影响→entity

**跨类型映射规则**:
- policy ↔ event: 政策的制定/颁布/废止是event，政策的内容/效力/影响是policy
- policy ↔ entity: 政策的制定者/执行者/受影响者是entity，政策本身是policy
- policy ↔ phenomenon: 现象是政策的问题来源，政策是现象的干预手段
- policy ↔ concept: 概念是政策的理念基础，政策是概念的制度化落地

### 2.6 technology（技术）

**定义**: 用于解决问题、实现功能或提升效率的系统性方法、工具或工程体系。技术具有可操作性、可复制性和可改进性，是人类改造世界的核心手段。技术包括硬件技术、软件技术、工艺流程、工程方法等。

**判断标准**:
- 具有可操作性（可被实施、应用、部署）
- 具有功能导向（解决特定问题或实现特定功能）
- 具有技术架构或工程实现路径
- 具有迭代演化的可能性

**关键词信号**:
1. 技术 / 工程 / 工艺 / 方法
2. 算法 / 模型 / 架构 / 框架
3. 芯片 / 半导体 / 处理器 / GPU
4. 人工智能 / 机器学习 / 深度学习 / 神经网络
5. 5G / 6G / 通信 / 网络
6. 量子 / 纳米 / 生物 / 基因
7. 自动驾驶 / 机器人 / 无人机 / 自动化
8. 云计算 / 大数据 / 物联网 / 边缘计算
9. 区块链 / 加密 / 去中心化 / 智能合约
10. 电池 / 储能 / 光伏 / 核聚变
11. 疫苗 / 靶向药 / 基因编辑 / 免疫疗法
12. 材料 / 合金 / 复合 / 超导
13. 卫星 / 火箭 / 空间站 / 深空探测
14. 制造 / 3D打印 / 数控 / 精密加工
15. 操作系统 / 编程语言 / 中间件 / 数据库
16. 传感器 / 执行器 / 控制器 / 嵌入式

**边界案例处理规则**:
- 当技术同时是概念时（如"人工智能"），问理论原理和哲学含义→concept，问工程实现和应用→technology
- 当技术被政策监管时（如"AI监管法规"），问技术本身→technology，问监管框架→policy
- 当技术引发社会现象时（如"短视频算法导致信息茧房"），问技术机制→technology，问社会效应→phenomenon

**跨类型映射规则**:
- technology ↔ concept: 技术是概念的工程实现，概念是技术的理论基础。核心判据：问"能不能做/怎么做"→technology，问"是什么/为什么"→concept
- technology ↔ policy: 技术是政策的监管对象，政策是技术的治理框架。问技术能力→technology，问监管规则→policy
- technology ↔ entity: 技术的开发者/拥有者是entity，技术本身是technology
- technology ↔ system: 技术是系统的组件，系统是技术的集成。问单一技术→technology，问技术体系→system

### 2.7 person（人物）

**定义**: 具有独立身份和能动性的个体人类主体。人物具有生平经历、社会角色、思想观点和行为影响，是历史叙事和社会分析的核心行动者。当问题聚焦于个体本身（而非其代表的组织或事件）时，归入此类型。

**判断标准**:
- 具有可辨识的个人身份
- 问题聚焦于个体本身（生平、思想、决策、影响）
- 具有社会角色和行动能力
- 不可被组织身份完全替代

4. 科学家 / 学者 / 教授 / 研究员
5. 作家 / 艺术家 / 导演 / 音乐家
6. 将军 / 军官 / 指挥官 / 统帅
7. 运动员 / 教练 / 裁判
8. 思想家 / 哲学家 / 理论家
9. 政治家 / 外交官 / 活动家
10. 发明家 / 工程师 / 程序员
11. 生平 / 传记 / 经历 / 履历
12. 思想 / 观点 / 主张 / 立场
13. 决策 / 选择 / 行动 / 作为
14. 影响 / 遗产 / 传承 / 评价
15. 成长 / 崛起 / 衰落 / 转型
16. 人格 / 性格 / 价值观 / 信仰

**边界案例处理规则**:
- 当人物与实体高度绑定时（如"马斯克"），问个人生平/决策/思想→person，问其企业/组织→entity
- 当人物是事件核心时（如"泽连斯基在俄乌战争中的角色"），问人物本身→person，问战争进程→event
- 当人物代表概念时（如"凯恩斯"），问人物生平→person，问其理论→concept

**跨类型映射规则**:
- person ↔ entity: 人物可创建/领导实体。问个人→person，问组织→entity。判断标准：问题是否聚焦于个体属性
- person ↔ event: 人物是事件的参与者和推动者。问人物角色→person，问事件过程→event
- person ↔ concept: 人物是概念的创造者。问人物生平→person，问理论内容→concept
- person ↔ technology: 人物是技术的发明者/推动者。问人物→person，问技术→technology

### 2.8 system（系统）

**定义**: 由多个相互作用的组件构成的复杂有组织结构，具有整体性、层次性和涌现性。系统不是其组件的简单加总，而是通过组件间的交互产生整体行为和涌现属性。系统包括自然系统（生态系统、气候系统）、社会系统（经济系统、教育系统）、技术系统（互联网、供应链）等。

**判断标准**:
- 具有多组件结构（非单一实体）
- 组件间存在交互和依赖关系
- 具有涌现性（整体行为不可从单一组件推导）
- 具有边界和与环境的交互

**关键词信号**:
1. 系统 / 体系 / 体制 / 机制
2. 生态 / 生态圈 / 生态链 / 生态系
3. 供应链 / 产业链 / 价值链 / 食物链
4. 经济体 / 市场体系 / 金融体系
5. 教育体系 / 医疗体系 / 社保体系
6. 国际秩序 / 世界体系 / 全球治理
7. 互联网 / 网络体系 / 信息基础设施
8. 交通网络 / 物流网络 / 能源网络
9. 政治体制 / 治理体系 / 行政体系
10. 运行机制 / 协调机制 / 反馈机制
11. 耦合 / 交互 / 联动 / 协同
12. 涌现 / 自组织 / 临界 / 相变
13. 稳态 / 均衡 / 失衡 / 崩溃
14. 输入 / 输出 / 反馈 / 调节
15. 开放系统 / 封闭系统 / 复杂系统 / 动态系统
16. 底层架构 / 基础设施 / 支撑体系 / 底座

**边界案例处理规则**:
- 当系统与实体重叠时（如"欧盟"），问组织身份→entity，问运作机制→system
- 当系统与政策重叠时（如"医疗体系改革"），问系统结构→system，问改革政策→policy
- 当系统与现象重叠时（如"全球经济失衡"），问系统结构→system，问失衡表现→phenomenon

**跨类型映射规则**:
- system ↔ entity: 实体是系统的组件，系统是实体的整合。问单一组织→entity，问多组织协同→system
- system ↔ policy: 政策是系统的治理工具，系统是政策的作用对象。问制度安排→policy，问运行逻辑→system
- system ↔ phenomenon: 系统产生现象，现象反映系统状态。问结构机制→system，问外在表现→phenomenon
- system ↔ technology: 技术是系统的功能组件，系统是技术的集成平台。问单一技术→technology，问技术体系→system

## 3. 路由决策流程

```
输入文本
  │
  ▼
┌─────────────────────────────────────┐
│ Step 1: 关键词扫描                   │
│ 对输入文本执行八类关键词信号匹配       │
│ 记录每类命中数量和命中位置             │
└──────────────┬──────────────────────┘
               │
               ▼
┌─────────────────────────────────────┐
│ Step 2: 语境消歧                     │
│ 对命中≥2类的候选类型执行语境分析       │
│ 判定问题焦点（问什么 vs 提到什么）     │
└──────────────┬──────────────────────┘
               │
               ▼
┌─────────────────────────────────────┐
│ Step 3: 优先级排序                   │
│ 对剩余候选类型按优先矩阵排序           │
│ 选择优先级最高的类型                   │
└──────────────┬──────────────────────┘
               │
               ▼
┌─────────────────────────────────────┐
│ Step 4: 最终分类                     │
│ 输出 object_type + object_category   │
│ 标注跨类型关联（如有）                │
└─────────────────────────────────────┘
```

### Step 1: 关键词扫描

对输入文本逐一匹配八类关键词信号列表，记录：
- 每类命中关键词数量
- 命中关键词在文本中的位置和上下文
- 命中强度（精确匹配 > 词根匹配 > 语义近似）

**命中阈值**: 单类命中≥2个信号词，或命中1个但为核心信号词（加粗标记的信号词），则该类进入候选集。

### Step 2: 语境消歧

当候选集包含≥2种类型时，执行语境分析：

1. **焦点判定**: 问题的核心追问是什么？被提及但非焦点的内容不决定分类
2. **动词分析**: 问题中的核心动词指向哪种类型的典型行为
3. **限定词分析**: "的"字结构中中心词归属哪类
4. **意图推断**: 用户真正想了解的信息类型

**消歧规则**:
- 提及≠归属：文本中提到某类对象不代表问题就是关于该类对象
- 焦点优先：问题焦点所在的类型优先于背景提及的类型
- 动词导向：核心动词的典型宾语类型具有强指示性

### Step 3: 优先级排序

当语境消歧后仍有≥2种候选类型时，按优先矩阵（第5节）排序。

### Step 4: 最终分类

输出 `object_type`（主类型）和 `object_category`（次级分类标签），并在 `object_category` 中标注跨类型关联信息。

## 5. 跨类型冲突优先矩阵

当输入文本经关键词扫描和语境消歧后，仍有≥2种候选类型无法区分时，按以下优先矩阵裁决。

### 5.1 优先级排序原则

优先级从高到低排列的核心逻辑：**具体性优先于抽象性，人的主体性优先于客体性，动态性优先于静态性**。

| 优先级 | 类型 | 优先理由 |
|--------|------|----------|
| 1 | **person** | 人的主体性最高，当问题聚焦于个体时，个体归属优先于其所代表的组织/事件/概念 |
| 2 | **event** | 事件具有时间锚定和因果结构，具体性高于抽象类型 |
| 3 | **policy** | 政策具有权威性和规范性，具体性高于现象和概念 |
| 4 | **technology** | 技术具有可操作性和工程性，具体性高于纯概念 |
| 5 | **phenomenon** | 现象具有可观测性，但抽象性高于前四类 |
| 6 | **system** | 系统强调结构和涌现性，整体性高于单一实体 |
| 7 | **entity** | 实体是基础承载者，当无法归入更具体类型时归入 |
| 8 | **concept** | 概念是最抽象的类型，仅当无法归入其他七类时使用 |

### 5.2 两两冲突裁决表

| 冲突对 | 胜出类型 | 裁决理由 |
|--------|----------|----------|
| person vs entity | person | 人名首先指向个人，除非问题明确指向其代表的组织 |
| person vs event | person | 人物是事件的行动者，焦点在人时优先 |
| person vs concept | person | 人物是概念的创造者，问人本身优先 |
| event vs policy | policy | 政策的效力持续性高于事件的瞬时性，除非问事件过程 |
| event vs phenomenon | event | 事件是具体发生，现象是模式抽象，具体优先 |
| event vs technology | event | 事件的时间锚定性高于技术的持续性 |
| policy vs phenomenon | policy | 政策具有规范性效力，现象仅是描述性 |
| policy vs concept | policy | 政策是概念的制度化，具体性更高 |
| policy vs technology | 看语境 | 政策侧重治理，技术侧重实现，按问题焦点裁决 |
| technology vs concept | technology | 技术是概念的实现，可操作性更高 |
| technology vs phenomenon | technology | 技术具有可操作性，现象仅是可观测性 |
| technology vs system | system | 系统是技术的集成，整体性更高 |
| phenomenon vs concept | phenomenon | 现象具有经验基础，概念是纯抽象 |
| phenomenon vs system | system | 系统是现象的结构根源，解释力更高 |
| system vs entity | system | 系统强调交互和涌现，实体仅是组件 |
| entity vs concept | entity | 实体具有可指称性，概念是纯抽象 |

### 5.3 优先矩阵使用规则

1. **仅在语境消歧失败后使用**: 优先矩阵是最后裁决手段，不得跳过语境消歧直接使用
2. **默认分类不替代语境分析**: 第4节中的默认分类仅适用于语境完全不明确的情况
3. **跨类型关联必须标注**: 使用优先矩阵裁决后，必须在 `object_category` 中标注被覆盖的候选类型
4. **裁决理由必须记录**: 在 T01 的 self_check 中，使用优先矩阵裁决的案例必须说明裁决理由

## 7. 路由自检清单

T01 Sub-Agent 在输出 `object_type` 前，必须逐项确认：

- [ ] 是否对输入文本执行了完整的关键词扫描（八类全部扫描）？
- [ ] 当候选类型≥2种时，是否执行了语境消歧？
- [ ] 语境消歧是否基于问题焦点而非背景提及？
- [ ] 当语境消歧无法解决时，是否按优先矩阵裁决？
- [ ] 优先矩阵裁决是否记录了裁决理由？
- [ ] `object_category` 是否标注了跨类型关联信息？
- [ ] 分类结果是否与第4节的边界案例规则一致？
- [ ] 是否避免了"提及即归属"的错误（提到≠关于）？
